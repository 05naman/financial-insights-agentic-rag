# Evaluation

How I measure whether the system works, and why the eval is built the way it is. Read this before an interview.

## What the eval answers

1. **Retrieval:** does the right page come back in the top 6? (no LLM involved)
2. **Answering:** is the final answer correct, cited, and backed by its sources?
3. **Does the agent help?** The same questions run through three systems:
   - `naive`: dense search only, one LLM call (the baseline)
   - `hybrid`: dense + BM25 + reranker, one LLM call
   - `agentic`: the full agent (plan, retrieve, grade, calculate, answer, verify)

## The dataset

`backend/evals/questions.json`, 62 questions, generated by `backend/scripts/make_mock_reports.py`.

**Why mock reports?** I generate the annual reports myself (three fictional Indian companies, FY2022 to FY2024), so
every answer is known exactly and nothing depends on a human labelling real PDFs. The layout copies patterns from
real reports I inspected (borderless tables, two-column pages, running headers, "(Rs in crore)" unit lines, Indian
digit grouping like 2,40,893, current and previous year columns). Ingestion was also run on two real reports from NSE's
archive to check the parser on real layouts.

**Why this is honest to say:** the mock set measures the pipeline and the agent logic. It does not prove accuracy on
every real PDF; that depends on parsing quality, which is why the cited page is always shown so a user can verify.

| Category | n | What it tests | Difficulty |
|---|---|---|---|
| single_fact | 18 | read one number from one report (revenue, PAT, employees, dividend, assets, cash) | easy |
| paraphrase | 3 | same facts in different words ("turnover", "net profit", "head count") | medium |
| multi_year | 9 | growth between years, figures from several reports, margin over 3 years | medium |
| segments | 3 | largest segment and its revenue | medium |
| risks | 6 | summarise risks; find which company mentions a given risk | medium/hard |
| multi_company | 5 | compare companies, rank companies | medium/hard |
| calculation | 9 | CAGR, net profit margin, debt-to-equity (needs the calculator) | hard |
| follow_up | 3 | "And in FY2023?" depends on the previous turn | hard |
| unanswerable | 6 | must refuse: future values, share price, a company not in the set, advice, data not disclosed | medium |

Each item records `category`, `difficulty`, `reasoning` type, `expected_contains` (answer facts), `gold` (the
company-year and acceptable pages where the answer lives; discovered by searching the generated PDFs, not hard-coded)
and, for follow-ups, the prior conversation.

## Metrics

| Metric | Definition |
|---|---|
| **Retrieval recall@6** | share of gold locations (company-year) for which at least one acceptable page is in the top 6 |
| **Accuracy** | every group in `expected_contains` appears in the answer (digits compared with commas and spaces removed, alternatives allowed, e.g. rounding). Unanswerable items pass only if the answer says "Insufficient evidence". |
| **Citation correct** | the answer cites every expected company-year |
| **Grounded** | every non-trivial number in the answer appears in the passages it cited (checks for invented figures) |
| **Latency / LLM calls** | cost of the extra agent steps |

Scoring is deterministic string matching on purpose: no LLM judge, so results are repeatable and cheap, and there is no
"model grading its own homework" problem. The cost is that a correct answer in unexpected wording can be marked wrong
(the failures are listed in each report so they can be read by a human).

## Running it

```bash
cd backend
uv run python scripts/make_mock_reports.py                  # regenerate PDFs, questions.json
uv run python -m app.cli ingest --dir ../data/pdfs
uv run python -m evals.run --retrieval-only                 # retrieval only, no LLM
uv run python -m evals.run --modes naive hybrid agentic     # everything
uv run python -m evals.run --modes agentic --category calculation --limit 5
```
Reports are saved in `backend/evals/results/`.

## Results

Retrieval (top-6, 53 non-follow-up answerable questions), from `evals/results/`:

| Setup | Raw question | With company/year filters |
|---|---|---|
| dense only | 71% | 91% |
| hybrid (dense + BM25) | 74% | 95% |
| hybrid + reranker | 64% | 94% |

What this shows, and what I would say about it:

- **Without filters, retrieval is weak** because all reports share a template: a page about FY2024 revenue looks like
  the page about FY2023 revenue. Embeddings capture meaning, not "this exact year".
- **The planner's metadata filters (company, year) are the biggest lever:** +20 points. This is a concrete reason to
  have an agent that plans before it searches.
- **Hybrid beats dense** (exact figures and names benefit from BM25).
- **The cross-encoder reranker did not help here**, and costs about 2 seconds on a CPU. It does not understand company
  or year, and a generic passage-ranking model is not trained on financial tables. I would not claim it helps; with real
  reports, with larger corpora, it may. This is an honest negative result and worth stating.

Answer quality: see the latest file in `backend/evals/results/` (the table is generated, not hand-written).

## Retrieval stress test (246 hard queries, no LLM)

`evals/retrieval_stress.py` asks the search 246 realistic questions and checks the right page comes back. Groups:
literal wording, synonyms, year written 7 ways, company written 5 ways, typos, exact figures (`1,89,866`), two
companies in one question, two years in one question, chatty questions, and **held-out wording** (see below).

```bash
cd backend
uv run python -m evals.retrieval_stress --limit 5        # 5 mixed cases, each result printed as it finishes
uv run python -m evals.retrieval_stress --category typos # one group
uv run python -m evals.retrieval_stress                  # all cases, ~10 seconds
uv run python -m evals.retrieval_stress --ablate         # switch each improvement off in turn
uv run python -m evals.retrieval_stress --variants       # add improvements one by one
```

**Result on the real index** (found the right page in the top 6 / ranking quality, 1.00 = always first):

| Group | Plain hybrid | With improvements |
|---|---|---|
| exact figures | 56% / 0.35 | **100%** / 0.69 |
| typos | 79% / 0.40 | **100%** / 0.85 |
| multi-company | 100% / 0.92 | 100% / 1.00 |
| year written differently | 100% / 0.85 | 100% / 1.00 |
| **All 246** | **89% / 0.74** | **99% / 0.85** |

**What each improvement is worth** (measured by removing it from the full setup, `--ablate`):

| Improvement | Why | Verdict |
|---|---|---|
| Company name in each passage's search header | queries use names, passages only had tickers | biggest win: ranking 0.89 → 0.73 without it |
| Numbers indexed without commas | the keyword index split `1,89,866` into `1`, `89`, `866` | exact figures 100% → 72% without it |
| Typo correction against the reports' own vocabulary | `employes`, `riscs`, `revnue` | typos 100% → 75% without it |
| Auto-detect company and year in the question | `bhit ... FY24`, `2023-24`, `March 2024` | cleaner results, fills gaps the planner leaves |
| Dropping heading-only chunks | tiny fragments looked like noise | **no gain, so it is off** |
| Finance synonym list (`turnover` → revenue) | plain-English wording | **no gain on unseen wording, so it is off** |

**An honest note on overfitting.** The synonym list first looked like a win (+15 points on the "synonyms" group). That
group's phrasings were in my head when I wrote the list, so it was partly testing what I had memorised. I added a
**held-out group** of 42 phrasings the list had never seen ("surplus left after expenses and tax", "liquid funds held
by", "hazards facing"). On those, results were identical with and without the list, so it is switched off. The
improvements that stayed are general (they do not depend on specific words), and each one earned its place in the
leave-one-out run.

Options live in `app/core/config.py` (`index_*`, `query_*`). Changing an `index_*` option needs
`uv run python -m app.cli ingest --replace` to rebuild the index.

## Real report test (TCS annual report 2025-26, 360 pages)

The mock reports are 6 pages; a real one is 360. `evals/real_report.py` tests search on a real filing, with answer keys
read from the filing itself (consolidated profit and loss on p.167, dividend on p.238, and so on). The PDF is kept in
`data/pdfs` (git-ignored); only the questions and answer keys are in the repo (`evals/real_reports/tcs_fy2026.json`).
A question counts as found when one of the top 6 passages contains the expected figure.

```bash
cd backend
uv run python -m evals.real_report --limit 5                    # a small batch, each result printed as it finishes
uv run python -m evals.real_report --limit 5 --offset 5         # the next batch
uv run python -m evals.real_report --group synonyms             # one group
uv run python -m evals.real_report --variants production,boost  # compare ranking rules side by side
```

**The sample-data tuning did not carry over.** On the sample reports 99% of questions were found; on the real report
plain hybrid search found only 60% (30 questions). The causes were different from anything the sample data showed:

| Real-world problem | What happened | Fix |
|---|---|---|
| Notes outrank the statement | "net income" matched dozens of *Notes* pages (deferred tax, other income) instead of the profit and loss statement | **tag primary-statement tables and boost them on money questions** (below) |
| Spaces inside bold numbers | `**2, 7 1, 423**` instead of 2,71,423 (letter-spaced PDF font): breaks search and the number check | repair step in the loader (whole numeric table cells only, so two numbers are never glued) |
| Corrupted font encoding | 10 of 360 pages (0.1% of text) come out as `�` or wrong letters (`attriutae`) | not fixed; the key statements are clean. The agent refused to guess from those pages |
| Rupee sign read as "H" | `H31.00` for ₹31.00 | cosmetic, left as is |
| Junk passages (page footers, lone headings) | seen ranking #1 for some queries | **dropping them did not help** (26/30 vs 27/30), so it stays off, matching the sample-set result |
| Repeated page headers ("Notes forming part of ...") | soak up matches on dozens of pages | **stripping them more aggressively (15% of pages, not 40%) did not help** (26/30 vs 27/30), so the default stays |

**The primary-statement boost.** Passages under "Statement of Profit and Loss", "Balance Sheet", "Cash Flow" and
"Financial Highlights" are tagged at indexing time (a metadata tag, so older indexes only need `python -m app.cli retag`,
no re-embedding). On a question about money, those passages get extra ranking score. It applies only to money questions:
boosting every question dropped the sample set from 99% to 96%, mostly by pulling risk questions toward financial tables.

| Set | Before | After |
|---|---|---|
| Real TCS report, 30 questions: found in the top 6 / ranking quality | 60% / 0.34 | **90% / 0.63** |
| Real TCS, reworded questions ("net income", "total sales", "gross receipts") | 17% | **83%** |
| Sample reports, 246 questions | 99% / 0.85 | 99% / 0.85 (no harm) |

**Still missing on the real report:** "bottom line", "what TCS paid its people" and one long chatty question, because
nothing in them looks like a money term to the detector. The agent's planner (an LLM) is the intended answer to that.

**Agent on the real report (first look, 2 of 5 questions before the free quota ended):** revenue was answered
correctly (₹2,67,021 crore, cited p.58 and p.225, figures verified, 4 LLM calls). For profit it said "insufficient
evidence" instead of guessing, because search had not yet reached page 167 (fixed by the boost). Not yet re-run.

## Likely interview questions

- *Why not just use an LLM judge?* Repeatability, cost, and bias; deterministic checks catch the failures that matter
  most (wrong or invented numbers). A judge would be added for free-text answers like risk summaries.
- *How do you know the agent is better, not just different?* Same questions, same data, same LLM; only the system
  changes. Compare per category and per difficulty, not just the overall number.
- *What if the model gets lucky?* Each question is single-run; temperature is low (0.1). Running each question several
  times and reporting the variance is the next step.
- *What does the eval not cover?* Real-PDF parsing errors, scanned documents, and questions written by real users.
- *Why separate retrieval and answer metrics?* To know whether a wrong answer is a search failure or a reasoning
  failure; the fix is different.
- *Data leakage?* The questions come from generated numbers the model has never seen, so it cannot answer from memory;
  the "company not in the set" and "FY2025" questions check that it does not try.
